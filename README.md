# Хэсэг A: Category-Partition гараар — Шилжүүлгийн функц

Тест дизайн хийх функц (код байхгүй, зөвхөн тодорхойлолт):

```
POST /transfer  { "from": ID, "to": ID, "amount": NUM, "currency": CODE }
```

## Олон алдааны давуу эрэмбэ

Нэг хүсэлтэд хэд хэдэн алдаа зэрэг байвал аль нь буцахыг тодорхойлолтод зориуд бичээгүй. Иймд давуу эрэмбийг өөрөө дараах байдлаар тогтоов: **from → to → amount**, мөн amount-ын дотор **BAD_AMOUNT → INSUFFICIENT → LIMIT**. Ингэснээр бүтэн эрэмбэ нь:

`NO_FROM → FROZEN → NO_TO → SAME_ACCOUNT → BAD_AMOUNT → INSUFFICIENT → LIMIT`

**Үндэслэл:** тодорхойлолтод алдааны кодууд яг энэ дарааллаар жагсаагдсан бөгөөд "эхлээд оролтын объектууд (данс) байгаа эсэхийг, дараа нь дүнг шалгадаг" гэсэн логик утгатай. Давхар нөхцөлийн спецификаци болон PICT-ийн олон алдаатай мөрийн oracle энэ эрэмбээс хамаарна.

## Даалгавар A1 — Сонголт ба төлөөлөх утгууд

| Параметр | Сонголт ба төлөөлөх утгууд | Тайлбар |
| :--- | :--- | :--- |
| **from** (данс) | Valid, Frozen, Missing | Байгаа / царцсан / байхгүй |
| **to** (данс) | Valid, Missing, SameAsFrom | Байгаа / байхгүй / from-той ижил |
| **amount** (дүн) | Normal, ExactBalance, Zero, OverBalance, OverLimit | `ExactBalance` нь хилийн утга: үлдэгдэлтэй яг тэнцүү |
| **currency** (валют) | Same, Different | Данснаас ижил / өөр валют |

### Далд орчны сонголтууд ба тооцооллын тайлбар

Тест дизайнд дараах далд орчны (environmental) сонголтууд нөлөөлөх бөгөөд үүнийг тест кейс бүрийн setup хэсэгт тодорхой зааж өгнө (жишээ нь: "from данс: 1000 USD, өдрийн лимит: 5000 USD, өнөөдөр зарцуулсан: 0 USD"):

- **Дансны үлдэгдэл:** OverBalance, ExactBalance нөхцөлийг тодорхойлоход дансны одоогийн үлдэгдлийн хэмжээ орчин болж оролцоно.
- **Өдрийн лимит хэр дүүрсэн байдал:** Лимитийн төлөв нь хоосон (өмнө нь гүйлгээ хийгээгүй) эсвэл дүүрэх дөхсөн (өдрийн лимитийн дийлэнх хэсгийг ашигласан) байж болно. Иймд жижиг хэмжээний amount хүртэл нийлбэр дүнгээрээ өдрийн лимитээс хэтрэх боломжтойг анхаарна.
- **Валютын ханш:** Different буюу өөр валюттай үед ханшийн хөрвүүлэлт хийгдэх тул ханшийн орчин шаардлагатай бөгөөд үлдэгдэл болон лимитийг хөрвүүлсний дараах дүнгээр шалгана.

> *Тайлбар:* Дээрх далд орчны тоон утгууд нь тест кейсийн бодит setup-ыг бүрдүүлэх боловч Category-Partition-ий бүрэн болон хязгаарлалтын дараах олонлогийн тооцооны үржвэрт тусдаа параметр болж орохгүй (эс бөгөөс боломжит хувилбарын тоо хэт өсөх тул үндсэн логик параметрээр хязгаарлав).

## Даалгавар A2 — Хязгаарлалтууд ба тэмдэглэгээ

| Параметр / Утга | Тэмдэглэгээ | Үндэслэл |
| :--- | :--- | :--- |
| **from = Frozen** | `[ERROR]` | ERROR_FROZEN буцна, үлдсэн шалгалт хийгдэхгүй. |
| **from = Missing** | `[ERROR]` | ERROR_NO_FROM буцна, бусад утга ач холбогдолгүй болно. |
| **to = Missing** | `[ERROR]` | ERROR_NO_TO буцна. |
| **to = SameAsFrom** | `[ERROR]`, `[IF from байгаа]` | `from` байгаа үед л хооронд нь харьцуулж "ижил" эсэхийг шалгана. |
| **amount = Zero** | `[ERROR]` | amount ≤ 0 тул ERROR_BAD_AMOUNT буцна. |
| **amount = OverBalance** | `[ERROR]` | Дансны үлдэгдлээс хэтэрсэн тул ERROR_INSUFFICIENT буцна. |
| **amount = OverLimit** | `[ERROR]` | Өдрийн лимитээс хэтэрсэн тул ERROR_LIMIT буцна. |
| **amount = ExactBalance** | `[SINGLE]` | Хилийн утга. Нэг удаа шалгахад хангалттай, бусад утгатай хосолж үржүүлэх шаардлагагүй. |
| **currency = Different** | (энгийн) | Happy path болон энгийн урсгалд хоёр утгыг хоёуланг нь шалгана. |

### Бүрэн олонлог ба хязгаарлалтын дараах тооцоо (N → M)

- **Бүрэн олонлог (N):** 3 (from) × 3 (to) × 5 (amount) × 2 (currency) = **90**
- **Хязгаарлалт, тэмдэглэгээний дараах тоо (M):**
  - `[ERROR]` утга тус бүр нэг тест: 2 (from) + 2 (to) + 3 (amount) = **7**
  - `[SINGLE]` (`ExactBalance`) нэг удаа: **1**
  - Алдаагүй утгуудын хослол: from=Valid × to=Valid × amount=Normal × currency(2) = **2**
  - Нийт: 7 + 1 + 2 = **10**
- **Дүгнэлт: 90 → 10**

# Хэсэг B: PICT — pairwise covering array

## Даалгавар B1 — Лекцийн браузерын жишээ

`browser.model`:

```
Content:   Allow, Restrict, Block
Cookies:   Allow, Restrict, Block
Popups:    Yes, No
Addons:    Yes, No
Attacks:   Yes, No
Forgeries: Yes, No
```

Ажиллуулсан:

```bash
pict browser.model | tee results/browser-2way.txt
pict browser.model /o:3 > results/browser-3way.txt
tail -n +2 results/browser-2way.txt | wc -l    # 10
tail -n +2 results/browser-3way.txt | wc -l    # 20
```

| Хамралт | Мөрийн тоо | Бүрэн олонлог (144)-д эзлэх хувь |
| :--- | :---: | :---: |
| 2-way (pairwise) | **10** | 6.9% |
| 3-way | **20** | 13.9% |

**2-way: яагаад 9 биш 10 мөр гарав?** Лекц дээр гараар 9 мөрөнд багтаасан. Content × Cookies хоёр 3 × 3 = 9 хостой тул 9-өөс цөөн мөр байх боломжгүй, харин PICT нэг мөр илүү өгсөн. `results/browser-2way.txt`-д (Allow, Block) хос 4 дэх болон 10 дахь мөрөнд **хоёр удаа** гарсан нь үүнийг харуулна. PICT нь **greedy** (шунахай) алгоритм ашигладаг. Алхам бүрт одоогоор хамрагдаагүй хосыг хамгийн их хамрах мөрийг сонгодог, гэхдээ ирээдүйн алхмуудыг төлөвлөдөггүй тул хамгийн цөөн мөрийг **заавал** өгдөггүй. Хамгийн цөөн covering array олох нь NP-хэцүү бодлого учраас PICT хурдыг сонгож, үр дүнгээрээ оновчтой дөхсөн боловч заавал оновчтой биш шийдэл өгдөг. Гараар хийсэн 9 мөр нь хүн Content × Cookies хосыг эхэлж бүрэн хуваарилж, бусад баганыг түүнд тааруулсны үр дүн юм.

**3-way:** 144 мөрийн оронд **20** мөр гарсан (13.9%). Теорийн доод хязгаар нь 3 × 3 × 2 = 18, тиймээс PICT-ийн үр дүн ч доод хязгаарт ойрхон байна. Ингэснээр гурвын хослол бүрийг (жишээ нь Content × Cookies × Popups) хамарсан ч тестийн тоо бүрэн олонлогийн 1/7 орчим болж буурсан.

## Даалгавар B2 — Шилжүүлгийн модель PICT-ээр

A хэсгийн сонголт, утгуудыг PICT хэл рүү буулгав.

**`transfer-nc.model`** (хязгаарлалтгүй):

```
From:     Valid, Frozen, Missing
To:       Valid, Missing, SameAsFrom
Amount:   Normal, ExactBalance, Zero, OverBalance, OverLimit
Currency: Same, Different
```

**`transfer.model`** (A2-ын дүгнэлтээр хязгаарлалттай):

```
From:     Valid, Frozen, Missing
To:       Valid, Missing, SameAsFrom
Amount:   Normal, ExactBalance, Zero, OverBalance, OverLimit
Currency: Same, Different

IF [From] <> "Valid" THEN [To] = "Valid" AND [Amount] = "Normal";
IF [To] <> "Valid" THEN [Amount] = "Normal";
```

Хязгаарлалтын үндэслэл: A2-д from/to-ийн алдаа бүр `[ERROR]` тул тэдгээрийг хооронд нь болон алдаатай дүнтэй хослуулж болохгүй (error masking). Үүнд From нь Valid биш үед To=Valid, Amount=Normal; To нь Valid биш үед Amount=Normal гэж албадсан. Ингэснээр нэг мөрөнд хамгийн ихдээ нэг алдаа үлдэнэ.

**`transfer-neg.model`** (`[ERROR]` утгуудыг `~`-ээр тэмдэглэсэн):

```
From:     Valid, ~Frozen, ~Missing
To:       Valid, ~Missing, ~SameAsFrom
Amount:   Normal, ExactBalance, ~Zero, ~OverBalance, ~OverLimit
Currency: Same, Different
```

Ажиллуулсан:

```bash
pict transfer-nc.model  > results/transfer-nc.txt
pict transfer.model     > results/transfer.txt
pict transfer-neg.model > results/transfer-neg.txt
```

### Мөрийн тооны харьцуулалт

| Хувилбар | Нийт мөр | Happy path (0 алдаа) | 1 алдаатай | 2 алдаатай | 3 алдаатай |
| :--- | :---: | :---: | :---: | :---: | :---: |
| `transfer-nc` (хязгаарлалтгүй) | **15** | **0** | 5 | 6 | 4 |
| `transfer` (A2 хязгаарлалттай) | **16** | **2** | 14 | 0 | 0 |
| `transfer-neg` (`~` сөрөг утга) | **18** | **4** | 14 | 0 | 0 |

(`transfer-nc`, `transfer` дахь "алдааны тоо" нь Frozen, Missing, SameAsFrom, Zero, OverBalance, OverLimit утгын тоо. `transfer-neg`-д `~`-тэй талбарын тоо.)

Хэрэгжүүлсэн тоолох команд (`results/` дотор):

```bash
# нэг мөр дэх алдааны тоо (transfer-nc.txt, transfer.txt)
awk -F'\t' 'NR>1{n=0; for(i=1;i<=NF;i++) if($i ~ /^(Frozen|Missing|SameAsFrom|Zero|OverBalance|OverLimit)$/) n++; print n}' results/transfer.txt | sort | uniq -c
# transfer-neg.txt
awk -F'\t' 'NR>1{n=0; for(i=1;i<=NF;i++) if($i ~ /^~/) n++; print n}' results/transfer-neg.txt | sort | uniq -c
```

### Гаралтыг уншсан дүгнэлт

**Happy path гарсан уу?**

- `transfer-nc`: **үгүй**, 15 мөрийн нэгд нь ч бүх утга хүчинтэй байгаагүй. PICT алдааны утгуудыг энгийн утга шиг хосолж, ердөө 15 мөрөнд хос бүрийг багтаахын тулд хүчинтэй мөрийг гаргаагүй.
- `transfer`: 2 мөр гарсан боловч хоёулаа `Valid, Valid, ExactBalance` (Currency = Same/Different). Энгийн `Normal` дүнтэй happy path мөр **гараагүй**. Учир нь `Normal` утга нь From/To алдаатай мөрүүдэд албадан орсон тул Amount × Currency-ийн хосыг тэдгээр мөр хамарсан.
- `transfer-neg`: 4 мөр. Normal × Same/Different, ExactBalance × Same/Different гэсэн эерэг утгуудын хос бүр хамрагдсан.

**Нэг мөрөнд хэдэн алдаа орсон бэ?** `transfer-nc`-д 10 мөр (15-аас) 2 болон 3 алдаатай, жишээ нь `Frozen, SameAsFrom, Zero, Different` нь нэг мөрөнд гурван алдаа. **Ийм мөр юуг шалгаж байгаа нь тодорхой биш.** Давуу эрэмбээр зөвхөн ERROR_FROZEN буцах тул SameAsFrom болон Zero-ийн алдаа шалгагдахгүй, нуугдана (error masking). Хос хамрагдсан мэт тоологдож байгаа ч бодит хамрагдалт биш.

**`~` хэрэглэхэд A2-ын хязгаарлалт хэрэгтэй хэвээр үү?** Энэ model-д **үгүй**. `transfer-neg.model` нь ямар ч `IF` хязгаарлалтгүйгээр нэг мөрөнд хамгийн ихдээ нэг алдаа өгсөн (0 алдаа: 4, 1 алдаа: 14), энэ нь `transfer.model`-ийн хязгаарлалттай ижил үр дүн. PICT-ийн `~` нь [ERROR] тэмдэглэгээний үүргийг орлосон. Харин `~`-тэй ч хязгаарлалт хэрэгтэй хэвээр байх нөхцөл бол **эерэг утгуудын хоорондын боломжгүй хослол** (жишээ нь тодорхой Amount нь зөвхөн тодорхой Currency-тэй боломжтой бол). Манай model-д ийм хослол байхгүй тул хязгаарлалт шаардлагагүй болсон.

**`transfer` (16) ба `transfer-neg` (18)-ийн ялгаа.** `transfer`-д 14 алдаатай мөр = 7 алдааны утга × 2 валют. `transfer-neg`-д ч мөн 14 алдаатай мөр, нэмж эерэг утгуудын 4 хос (2 Amount × 2 Currency) тусдаа мөр болж байгаа учраас 18 болсон. `transfer-neg` нь Normal дүнтэй happy path-ийг баталгаатай гаргадаг тул энэ тал дээр `transfer`-аас илүү.

### Гаралтаас гаргасан бодит тест кейсүүд

Setup-ийн нийтлэг орчин: **ACC-1001** — USD данс, үлдэгдэл 1000 USD, өдрийн лимит 5000 USD, өнөөдөр зарцуулсан 0; **ACC-1002** — хүчинтэй хүлээн авагч данс; ханш: **1 EUR = 1.25 USD**.

| # | PICT мөр (эх файл) | Setup | Оролт (POST /transfer) | Oracle |
| :-: | :--- | :--- | :--- | :--- |
| **T1** | `Valid, Valid, Normal, Same` (transfer-neg) — **happy path** | ACC-1001, ACC-1002 хүчинтэй | `{"from":"ACC-1001","to":"ACC-1002","amount":100,"currency":"USD"}` | 201 `{"result":"OK"}` |
| **T2** | `Valid, Valid, ExactBalance, Different` (transfer-neg) — **happy path, хилийн утга** | Нийтлэг орчин. 800 EUR × 1.25 = 1000 USD, үлдэгдэлтэй яг тэнцүү | `{"from":"ACC-1001","to":"ACC-1002","amount":800,"currency":"EUR"}` | 201 `{"result":"OK"}` |
| **T3** | `Valid, Valid, ~OverBalance, Different` (transfer-neg) — **нэг алдаатай мөр** | Нийтлэг орчин. 1000 EUR × 1.25 = 1250 USD > 1000 USD үлдэгдэл. Өдрийн лимит (5000) хэтрээгүй | `{"from":"ACC-1001","to":"ACC-1002","amount":1000,"currency":"EUR"}` | 200 `{"result":"ERROR_INSUFFICIENT"}` (хөрвүүлсний дараах дүнгээр шалгана) |
| **T4** | `~Frozen, Valid, Normal, Same` (transfer-neg) — **нэг алдаатай мөр** | ACC-3003 царцаагдсан, ACC-1002 хүчинтэй | `{"from":"ACC-3003","to":"ACC-1002","amount":100,"currency":"USD"}` | 200 `{"result":"ERROR_FROZEN"}` |
| **T5** | `Frozen, SameAsFrom, Zero, Different` (transfer-nc) — **олон (3) алдаатай мөр** | ACC-3003 царцаагдсан, USD данс | `{"from":"ACC-3003","to":"ACC-3003","amount":0,"currency":"EUR"}` | 200 `{"result":"ERROR_FROZEN"}`. Давуу эрэмбээр from-ийн алдаа (FROZEN) эхэлж, SAME_ACCOUNT, BAD_AMOUNT-ийг нууна |
| **T6** | `Valid, Valid, ~OverLimit, Same` (transfer-neg) — **орчны нөлөө** | ACC-4004: үлдэгдэл 10000 USD, өдрийн лимит 5000 USD, өнөөдөр зарцуулсан 0. Үлдэгдлээс хэтрэхгүй, лимитээс хэтэрнэ | `{"from":"ACC-4004","to":"ACC-1002","amount":6000,"currency":"USD"}` | 200 `{"result":"ERROR_LIMIT"}` |

T5-аас харахад олон алдаатай мөрийн oracle нь давуу эрэмбээс бүрэн хамаарна. Давуу эрэмбийг өөрчилбөл (жишээ нь amount-ыг эхэнд) ERROR_BAD_AMOUNT буцах байсан тул энэ мөр "ямар алдаа ажиллав" гэдгийг нэг утгатайгаар шалгаж чадахгүй. Иймээс `~` ашигласан T3, T4, T6 нь илүү хүчтэй тест болно.

## Даалгавар B3 — Гараар (A3) ба PICT-ийн харьцуулалт

| Шалгуур | Гараар (Category-Partition, A3) | PICT |
| :--- | :--- | :--- |
| **Алдааны семантик** | Алдаа бүрийг хүн ойлгож, oracle-ийг давуу эрэмбээр тогтоодог: 12 мөрийн алдаа бүр нэг тодорхой кодтой. | Утгын утгыг мэддэггүй. `~`, хязгаарлалтыг хүн зааж өгөхгүй бол олон алдаатай (error masking) мөр гаргана (`transfer-nc`: 10/15). |
| **Хосын хамралт** | Хамралтыг баталгаажуулдаггүй. Хүн утгын хослолыг орхигдуулж болно. | Хос бүрийн хамралтыг **математикаар баталгаажуулна** (2-way, 3-way). |
| **Тестийн тоо** | Алдаа бүр нэг тест тул цөөн (10) ба тайлбартай. | Greedy тул хамгийн цөөн биш (10 vs 9) боловч параметр олон үед гараар хийх боломжгүй хэмжээнд хурдан. |
| **Хилийн/онцгой утга** | `[SINGLE]`, `ExactBalance`-ийг хүн зориуд оруулдаг. | Утга model-д байвал л хамруулна, хилийн утгыг өөрөө олохгүй. |
| **Давтагдах чадвар** | Хүнээс хамаарна. | Ижил model ижил гаралт өгнө. |

**Дүгнэлт:** A3 хүснэгт нь алдааны семантикийг (аль алдаа аль нөхцөлд, ямар давуу эрэмбээр буцах) илүү сайн барьдаг. PICT нь хосын хамралтыг баталгаажуулдаг. Хоёрыг хослуулж, `~` ашиглан PICT-д алдааны семантик заах нь хамгийн хүчтэй.

# Дүгнэлт

Category-partition нь тестийн оролтыг утга учиртайгаар хуваадаг тул A3 хүснэгтийн алдаа бүр нэг тодорхой oracle-тэй болж, "аль алдаа буцах вэ" гэсэн асуултад давуу эрэмбээр хариулсан. Харин гараар хийсэн хүснэгт хосын хамралтыг баталгаажуулж чаддаггүй бөгөөд параметр нэмэгдэх тусам хослолыг хүн орхигдуулах эрсдэл өсдөг. PICT нь энэ дутагдлыг нөхөж, browser жишээнд 144 хослолыг 2-way-ээр 10, 3-way-ээр 20 мөр болгон буулгасан. PICT нь greedy алгоритмтай тул лекц дээрх гар 9 мөрөөс нэг мөр илүү (10) өгсөн нь хамгийн цөөнийг заавал өгдөггүйг харуулсан. Хязгаарлалтгүй `transfer-nc` нь 15 мөрийн 10-д нь 2-3 алдаа зэрэг оруулж, happy path мөр огт гаргаагүй тул error masking-ээс болж тестийн утга алдагдсан. `transfer.model`-ийн хязгаарлалт энэ асуудлыг засаж нэг мөрөнд ≤1 алдаа болгосон ч Normal дүнтэй happy path мөр алдагдсан. `~` ашигласан `transfer-neg` нь ямар ч хязгаарлалтгүйгээр ≤1 алдаа, 4 happy path мөр өгсөн нь хамгийн цэвэр шийдэл болсон. Тиймээс PICT-д алдааны семантикийг заах `~` бол category-partition-ий `[ERROR]` тэмдэглэгээтэй яг дүйх хэрэгсэл юм. Хамгийн их бодол шаардсан алхам нь олон алдааны давуу эрэмбийг тогтоох ба хязгаарлалтыг хэт хатуу бичиж жинхэнэ хослолыг устгахгүй байх тэнцвэрийг олох явдал байв. Нөгөө талаас PICT-ийн гаралтыг бодит тест кейс болгохдоо setup (үлдэгдэл, лимит, ханш) өөрөө зохиож өгөх шаардлагатай байсан нь автомат хэрэгсэл ч хүний дизайнтай хослох ёстойг харуулсан.
